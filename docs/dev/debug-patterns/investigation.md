# 通用诊断手法 — 调试模式

覆盖：诊断三阶段、分层二分+字节级证据、先写复现测试再定罪、验证脚本先自证、实物验证>代码推测、假设先行验证滞后、tracing directive 陷阱。

> 本文件只收**跨领域通用的诊断手法**。各领域文件内遇到的「弯路」浓缩为模式内一行证据，不重复进本文件。

---

## 手法 1：诊断分三阶段，每阶段有独立的错误特征

**诊断-阶段**：

| 阶段 | 目标 | 典型信号 |
|------|------|---------|
| A. 链路通不通 | 确认连接能建、数据能收发 | 抓真实 payload 开始打印 |
| B. 协议对不对 | 确认帧结构符合期望 | 解析函数不再无声落到 fallback |
| C. 渲染对不对 | 确认 store 状态正确反映到 UI | 文本流追加、状态 chip 更新 |

**跳阶段是常见错误**：A 没确认就去改渲染（B 的 payload 没看到，渲染是蒙眼写）；B 没确认就去调 UI（解析落 fallback，UI 怎么调都不对）。**每一阶段第一步都是加一行日志抓真实数据**。

**适用**：联调新协议（ACP/MCP/LSP）；前端链路过长时的归因。

---

## 手法 2：分层二分 + 每层字节级证据

**诊断-分层**：链路（xterm→WS→PTY→tmux→pane）逐层二分，每层用该层原始证据：字节记录器（raw-mode 打时间戳）、`xxd`/`od -c` 看字节、`getBoundingClientRect` 量几何、`/proc/<pid>/cwd` 读进程态——**比在中间层加日志、比截图目测、比代码推测快得多**。「程序读到的」与「人眼看到的」在含转义/序列化的输出里可以完全不同。

**适用**：转义序列、格式串、几何布局、进程状态任何「对端输出被中间层改写」的怀疑。

---

## 手法 3：先写复现测试再定罪

**诊断-复现**：竞态类 bug 的 feedback loop 关键是**把事件投递顺序变成测试输入**（mock WebSocket 手动驱动 onopen/onclose/onerror 时序），而不是指望真实网络重现时序。竞态类 bug 的 RED 以「确定性最小单元」为准（单测/构造时序），页面级复现只作佐证——时序竞态连刷多次可能不复现。**先写复现测试再定罪**，避免修一个不存在的 bug（假设被测试证伪时就该换方向）。

**适用**：任何怀疑「时序/竞态/事件顺序」的 bug；假设「某路径不触发」时先用测试证伪。

---

## 手法 4：验证脚本必须先自证

**诊断-自证**：测量工具必须先验证自身可信，否则"看起来 PASS"实为测空气：
- `lsof | grep inotify` 非 sudo 下对别的进程输出恒空 → 改用 `readlink /proc/<pid>/fd/*`（权限无关）。
- 脚本传错标识（project name 而非 id）→ 被测资源根本没分配 → 假 PASS。脚本必须**先确认被测资源真的被分配**，再测释放。
- headless 截图无法区分 11px 量级差异 → 用几何测量（getBoundingClientRect/clientWidth）。
- 验证 CSS 覆盖看 computed style，不看 inline 属性。
- headless DOM renderer 与真实浏览器渲染后端可能不同（xterm DOM vs canvas renderer）→ 先 dump 确认渲染后端再选测量对象。

**适用**：任何自动化验证脚本/验证步骤；"验证通过但实际没生效"的排查。

---

## 手法 5：实物验证 > 文档 + 源码推测

**诊断-实物**：能看实际创建的产物（`/proc`、`/sys`、DB 内容、`/var/log`、sock 文件、浏览器 DOM/渲染结果）先看，再上代码搜索。`readlink /proc/<pid>/cwd` 5 秒看到的事实比读 1000 行源码推测更有说服力；`getBoundingClientRect` 一次实测比多轮截图/视觉描述可靠。权限受限时（perf/gdb 不可用），DB 内容 + 代码审计是替代证据链。**在页面里验证 store 状态，要确认模块实例是同一份（对比函数源码/引用），否则独立模块实例会误导**。

**适用**：任何「创建出来的东西不对」；「症状归属到层」——先看 top 里高 CPU 进程是哪个二进制，别被症状带偏到错误层。

---

## 手法 6：假设先行、验证滞后是最大的时间黑洞

**诊断-假设**：第一轮假设要快速用日志证伪/证实。错误模式：
- 假设「A 是原因」→ headless 无法复现 → 归咎测试环境，而不是加日志确认执行流与状态值。
- 第一个修复无效后继续在同一假设上叠加代码，而不是换方向。
- **console.log 是第一优先级诊断手段**：3 行日志揭露的真相（并发调用/双重初始化/状态值正确）比几百行代码分析多。
- 「用户动作前后变化」先排除周期任务/轮询的巧合，再归因到动作本身。
- 日志缺失的归因顺序：路径没走 → 日志级别被过滤 → 二进制没有该日志代码（`strings` 验证），逐一排除。
- headless 测不出 StrictMode+网络延迟组合 → 在用户环境加诊断再动手修。

**适用**：任何一轮以上未定位的 bug；用户报告无法本地复现的场景。

## 手法 7：tracing EnvFilter 的 crate 名用 `_` 不是 `-`

**诊断-日志**：`EnvFilter` 用 Rust module path 当 target，module path 里连字符不合法，`env!("CARGO_PKG_NAME")` 拿到的 `omniterm-dev` 会被静默拒绝、directive 退化成"全部过滤"——看起来像代码没打 log，其实 log 被 directive 挡了。**诊断信号**：改了 directive 之后整组 log 一起消失，换回 `info` 全局 level 又回来。**正确做法**：硬编码下划线形式（`omniterm_dev=debug`），别信 `CARGO_PKG_NAME`。

**适用**：后端日志全无/部分消失的排查；新增 crate target 时。

---

## 手法 8：测试用独立会话，禁碰用户活动会话

**诊断-隔离**：终端类自动化测试必须 `tmux new-session -d -s omniterm-test-*` 自建独立会话，**禁止激活用户正在查看的 `lt_*` 外部会话**（会把用户从移动端切走、干扰其工作）。复现前先确认已走到目标渲染分支（无活动会话时页面停在空态，截图恒相同 md5 就说明没复现到终端）。

**适用**：终端/xterm/tmux 相关的所有自动化验证。

## 手法 9：冻结候选线程归因内存/CPU 增长归属

**诊断-冻结归因**：多线程进程的内存/CPU 持续增长，要归属到具体线程时，**SIGSTOP 冻结候选线程、观测指标是否停止**，比猜代码路径快一个量级。做法：`kill -STOP <tid>` → 观测 RSS/CPU 10s → `kill -CONT <tid>` 恢复（冻结可安全恢复，不破坏进程）。实测「冻结某个 `notify-rx` 线程后 RSS 增长归零」即一次命中归属，之后再去读该线程所属模块的源码找机制。配套现场证据：`/proc/<pid>/task/<tid>/io` 的 `rchar` 增量（哪个线程在读/处理）、`/proc/<pid>/fdinfo/<fd>` 的 inotify watch 数（资源注册规模）、`/proc/<pid>/smaps` 的匿名段（堆膨胀构成）。

**弯路**：先查子进程树、全进程 rchar 采样、fd 持有者（`readlink /proc/*/fd/*`）都落空——「瞬时 open 不留 fd」「inotify 事件不改变 mtime」让基于文件变动的排查失效；冻结实验跳过了「找事件源」直接锁定线程归属，再回头读 notify 源码确认机制。

**适用**：任何「进程内存/CPU 持续增长、无崩溃无 OOM 日志」的泄漏排查；单线程 100% CPU 但主线程空闲时的归属判定。
