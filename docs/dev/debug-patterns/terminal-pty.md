# 终端与 PTY — 调试模式

覆盖：MasterWriter Drop 副作用、字节能到达≠语义能到达、跨进程分隔符选型、平替实现边缘语法、FitAddon 桌面像素常量、escape-time 时序矩阵、增量绘制 diff 流不可字节尾回放、轮询推送的时延下界、diff 流不可 latest-wins 聚合。

---

## 模式 1：第三方库 Drop 隐式副作用（PTY 变体）

**终端-Drop**：`portable_pty::MasterWriter::Drop` 会在 drop 时往 PTY fd 写 `\n + VEOF(0x04)`，raw mode 的 agent 收到 EOF 中断任务。writer fd 是 dup 出来的独立 fd，drop master 不失效。**从源头避免副作用**：不创建会 drop 时写 fd 的对象，用 `master.as_raw_fd()` 直接 `libc::write`，master drop 后 write 返 EBADF 自然退出。

**适用**：任何经 PTY 的进程清理路径；改清理逻辑先看库源码 Drop 实现。

**案例证据**：
- 2026-06-28 切换/删除会话时 agent 任务被中断（"像被 Ctrl+C"），strace 证实 drop 写 `\n\x04`，10 次 ~4 次复现。修复：不用 take_writer，writer 线程裸 fd 写。
- 2026-06-23 早期同根因：切换会话 TUI 多一行 + opencode 断联，drop 前显式 SIGHUP 的修复不充分。

## 模式 2：字节能到达 ≠ 语义能到达（时序分帧）

**终端-时序**：终端复用器（tmux/psmux）对字节流做时序敏感重新分帧：孤立 `\x1b` 等待 `escape-time`（默认 500ms）区分 Alt/功能键，两个 `\x1b` 合并成 `\x1b\x1b` 一次转发，对 TUI 是完全不同的键。**「延迟 + 无反馈」会诱导用户行为落入故障窗口**：单次 ESC 延迟 500ms 本身只是慢，但诱导快速重按恰好触发合并。对协议软件测「时序矩阵」（单发/窗口内连发/窗口外连发），字节级实测到达分组。

**适用**：经 tmux 的托管终端按键问题；所有把 tmux 当基础设施的产品应设 `escape-time` 0–50ms。

**案例证据**：
- 2026-07-26 opencode 无法中止任务（需连按两次 ESC）。raw-mode 字节记录器实测：100ms 间隔双 ESC 到达 pane 为单次 `\x1b\x1b`。修复：spawn client 时 `set-option -s escape-time 10`。

## 模式 3：跨进程文本协议的分隔符选型必须先验证中间层不改写

**终端-分隔符**：tmux `-F` 格式串里的**非打印字节**不原样输出，而是转成字面八进制文本（`\x1f` 变 `\037`）。选分隔符稳妥顺序：领域内被禁止出现的可打印字符（tmux session 名禁 `:`、路径禁 `\0`）> 控制字符（需逐层验证）。「程序读到的」与「人眼看到的」在含转义序列的输出里完全不同——验证输出用 `xxd`/`od -c` 看字节，不肉眼看渲染。

**适用**：任何经 shell/终端复用器/日志管道的文本协议分隔符；「我发的 X 为什么收到的不是 X」类问题第一步原样捕获对端输出。

**案例证据**：
- 2026-07-26 agent_watch 用 `\x1f` 做分隔符，Rust split 后 `parts.len()==1` 解析 0 个 pane。修复：改 `:` 分隔（session 名禁 `:`）+ 自由文本字段放末段 `splitn` 兜住。

## 模式 4：平替实现只保证主路径兼容，边缘语法是断裂带

**终端-平替**：drop-in replacement（psmux/busybox/mawk）对核心子命令兼容度高，但链式命令、引号展开、隐式默认值这类「语法胶水」最容易分岔。对平替实现只用最简单的单命令调用，复合需求拆成多次调用。**「退出码 0 + 无输出」是「命令被理解成另一种模式」的特征签名**（崩溃会非零退出，exit 0 说明程序认为自己的工作做完了——只是和你以为的不是同一件）。诊断交互式程序必须复制真实运行环境（TTY/ConPTY）——管道下 `isatty` 检测切换行为完全不同；目标程序发终端探针（DSR/DA）时诊断工具要扮演终端回复它。

**适用**：Windows 平替 tmux/psmux；任何「换了个实现行为就变」的场景。

**案例证据**：
- 2026-07-29 psmux 遇 `;` 链式命令进入一次性命令模式执行完 exit 0 不 attach → Windows 终端只剩 "attached" 提示无 shell。修复：按平台 cfg 拆分，windows 只跑纯 `new-session -A`，escape-time 单独一次性设置。

## 模式 5：第三方库的「桌面环境」像素常量假设在移动端失效

**终端-像素**：xterm FitAddon 固定预留 `DEFAULT_SCROLL_BAR_WIDTH=14px` 滚动条宽，且取容器 border-box 未扣 padding。触摸设备滚动条是 overlay（宽 0）→ 内容网格比容器右缘少 ~11px，黑色背景透出成「黑条」。**凡第三方库有桌面环境像素常量假设（滚动条宽/字体度量/光标形状），移动端视觉异常先 grep 库源码里的常量，再怀疑自己布局**。字体「测量宽度」与「渲染宽度」亚像素偏差在行尾累积成截断：最后一列溢出量 = 字形宽 − 测量 cellW（与列数无关），`.xterm-screen` 比 `cols × cellW` 略宽即有缓冲。移动端修复必须按比例/按运行时测量自适应（安全余量用 cellW 比例而非固定 px），CSS 相对单位覆盖 inline 像素宽。

**适用**：移动端终端渲染、任何第三方 UI 库的尺寸计算；「被遮挡/截断」先区分内容被裁 vs 内容没延伸到那里（量内容元素 vs 容器元素几何差）。

**案例证据**：
- 2026-08-04 移动端 tmux 右侧黑条（screen 367px vs viewport 378px，gap 11px）+ 行尾字符截断（余量 0.6px，临界视口宽度溢出被裁）。修复：覆盖 `fit.proposeDimensions` 按 clientWidth − padding 取整列数并预留 `0.13 × cellW` 余量 + 移动端隐藏原生滚动条 + `.xterm-screen`/行 div `width:100%` 并取消行 div `overflow: hidden`。

## 模式 6：增量绘制 diff 流不可按字节尾回放（字节流 ≠ 屏幕状态）

**终端-屏幕态**：TUI 程序的输出分两类——SIGWINCH 全量重绘型（vim/htop，收到尺寸变化信号即整屏重画）与增量绘制型（chat 型 agent CLI：光标绝对定位 + 局部擦除的 diff 流，每条序列依赖**上一帧的屏幕状态**）。对后者，重连补屏若只回放环形缓冲的原始字节尾（清屏后重放），序列会落在错误位置 → 花屏（文本块错位、残片）；且字节环可能从转义序列中间截断（半条 `\x1b[...`），resize nudge 也只救全量重绘型。**根因是概念混淆：回放的字节流 ≠ 客户端当前屏幕状态，diff 序列对「不存在的底图」求值必然错位**。正确做法：以服务端 VT 模拟器的 grid 为真相源整帧重渲染（带样式 + 光标定位/显隐复位），原始字节尾仅保留进 scrollback 与恢复模式态（alt-screen 等 DECSET）。「字节回放保真度更高」的直觉只对全量重绘型成立。

**适用**：一切「服务端维护终端模拟器 + 客户端消费 ANSI 流」的重连/补屏路径；凡补屏/回放设计，先问目标程序的绘制模型是全量重绘还是增量 diff。

**案例证据**：
- 2026-08-22 pty 会话跑 chat 型 agent TUI 重连花屏（截图证实文本块错位、右缘/底行残片）。修复：`VtState::render_screen()` grid 整帧重画接入补屏帧（raw 尾 + 清可见屏 + 重渲染），锁序 out→vt 保证快照/渲染/订阅原子；此前 Phase 2 切片 B 曾评估过 grid 重渲染并以「字节回放保真度更高」为由弃用——该判断未区分两类绘制模型。
- 2026-08-22 同根因续发：为救花屏引入的 resize nudge（rows-1 → 30ms → rows）在新机制下反而让重连后画面「整体上滚一行 + 顶部残片」——用真实会话字节流离线复现实证 alacritty shrink→expand 非内容中性。教训：**为旧机制设计的补偿手段，在新机制落地后要重新评估存废**；补偿与被补偿者同源（同一 grid）时会互相污染。

## 模式 7：轮询是推送唯一触发源时，周期即时延下界（突发渲染）

**终端-推送时序**：为限制编码/推送成本引入固定周期定时器（如 30fps）时，若它是**唯一**推送触发源，用户感知延迟下界 = 周期，快速连续输入的变化被聚合进同一帧、攒一批突然出现（「不实时」感）。判定签名：实测延迟均匀分布在 (0, 周期] 区间 + 快速输入时多行同帧出现。正确组合是**事件驱动即时编码 + 低频定时器兜底**——输出事件（广播帧到达）本身已携带「有新内容」信号，收到即编码推送；定时器只兜漏网路径（无事件的内部状态变化）。纯轮询只适合无事件信号的场景。**编码成本顾虑不靠抬高延迟解决**：真相源是服务端 grid 快照（读循环先 feed 再广播，收到事件时 grid 已最新），即时编码无正确性风险；行级 diff 已保证无变化时帧体近空。

**适用**：一切「服务端状态 → 周期采样 → 推送」的同步链路（终端帧、文件监听、状态面板）；「感觉不实时/突然跳变」先量推送触发源是事件还是定时器。

**案例证据**：
- 2026-08-25 pty 会话连按回车行「攒一批突然出现」。根因：cell_frame 编码只由 33ms 定时器触发，raw bytes 分支仅排干不编码。修复：`rx.recv()` 收到输出事件即编码推送，定时器降为兜底；实测回车→帧延迟 avg 11.1ms/max 13.1ms → avg 3.7ms/max 5.8ms。

## 模式 8：latest-wins 聚合只兼容快照型消息，不兼容 diff 型消息

**终端-聚合语义**：高频流的消费端做「只保留最新」聚合时，先问消息是**快照**（每条自带完整状态）还是 **diff**（相对上一条的增量）。快照流丢中间帧无损（最新即全部事实）；diff 流丢中间帧 = 那段增量**永久丢失**——服务端编码基线已前进，不会重发；症状是内容缺行/缺块，而「切换会话/重连走补屏全帧后又完整」（补屏以真相源整帧重画，恰好证伪了数据丢失、坐实了传输/渲染侧丢帧）。判定签名：**重连后完整、实时流缺块** → 丢的不是数据是帧。修法二选一：消费端按序渲染全部帧（聚合仅用于调度时机，不丢消息）；确要丢帧则必须配**重同步握手**（消费端告知生产端作废 diff 基线、下一帧发全帧）。另一个同诊断暴露的坑：**多观察者共享同一 diff 基线**——两连接交替编码会让各自的「相对上一帧」错位（全帧被另一个连接消费），diff 编码状态必须按连接隔离或强制单观察者。

**适用**：一切「服务端增量帧 + 客户端节流聚合」的推送链路（终端、画布、列表更新）；给聚合策略做正确性审查时先分类消息语义。

**终端-丢帧补偿自身被吞 = 补偿形同虚设**：丢帧配「重同步握手」还不够，要审**补偿路径自身的可靠性**——重同步请求被防刷屏节流吞掉（节流窗口内的第二次丢帧不再发重同步），与「没有补偿」等价。同时审查**被丢弃积压的帧语义**：快照型帧（full/overlay，自含完整状态）混在 diff 流里时，它既是「丢失可无损覆盖」的标记，也是**唯一自愈锚点**——把积压整体清空等于把锚点当 diff 一起丢；正确策略是**保留最后一个快照帧**（丢弃它之前的增量无损，渲染它即恢复），只对锚点之后的丢失配重同步。不变式：**「丢弃增量」必须对应「一份重同步在途」**，节流只能延迟发送、不能取消（补发定时器）。判定签名与上一条相同（切换会话/重连后恢复），区别在复现条件：本条需要**消费停摆跨过两次丢弃窗口**（如标签页隐藏数秒 + 期间 TUI 启动）。

**终端-无校准的增量镜像必不自愈（检测 + 兜底）**：上面的修复每轮堵一个具体漏水口（丢帧、补偿被吞、锚点漂移），但只要增量镜像的正确性继续依赖「基线推进序列 ≡ 前端渲染历史」这条**无人校验的不变式**，下一个扰动源冒出来症状依旧——前端没有任何机制能发现自己已失配，任何一次性扰动都造成不自愈的错位，直到走全帧路径（切换会话/重连/resize）才恢复，这正是该症状家族六轮修复仍复发的结构性根因。修法是把不变式从「假设」升级为「被守护的协议属性」，两件套缺一不可：① **检测**——帧序号（会话级单调递增，共享基线下必须 per-session 而非 per-connection，否则「增量被别的连接偷走」不可见），消费端校验 `seq == lastSeq + 1`，断链即主动重同步；② **兜底**——周期性全帧对账（时间驱动而非帧数驱动：低速输出时 N 帧跨度的上界不可控，时间驱动上界恒定），把一切失配的可见时间上界压到周期以内。检测提供即时收敛与观测数据（断链频率 ≡ 并发连接干扰频率），兜底覆盖检测不了的一切（含后端重启归零）。帧序号用 `Option` + 消费端对无序号帧跳过检测，使不占基线的旁路帧（viewport 窗口/overlay）天然豁免。

**案例证据**：
- 2026-08-25 pty 连按回车前端丢行（切换会话才补全）。根因：事件驱动编码（模式 7 修复）让帧率突破 30fps 后，前端 rAF latest-wins 开始真正丢 diff 帧。修复：前端改有界有序队列按序全渲染 + 超限发 `resync` 控制帧、后端作废 diff 基线下发全帧；浏览器实测连按 100 次回车可见屏 30/30 行无缺行，resync 后 41ms 收到全帧。
- 2026-09-04 pty 跑 codebuddy TUI 画在输入行上方、shell 回显残留底部（或整屏冻结在旧画面），切换会话恢复。根因：有序队列超限清空把积压中的 overlay/全帧一并清掉，且 1s 节流窗口内的再次超限不再发 resync——丢失的「清屏帧」永久无补偿，TUI 后续 diff 帧只画自己触碰的行，shell 行不被擦除。修复：超限时保留最后一个 full/overlay 帧为自愈锚点（keepFrom 策略），节流窗口内的清空安排补发定时器保证「清空必有重同步在途」；rAF 停摆 8s + TUI 启动实测修复前永久冻结、修复后正常显示且全帧补齐。
- 2026-09-08 pty 症状家族第六次复发（运行中画面错位/延迟，切换会话恢复），前五轮各堵一个漏水口后仍由新扰动源触发。结构性结论即本条规律：稳态无周期全帧、无帧序号，失配不可检测也不自愈。修复：`CellFrame.seq`（`VtState` 会话级计数，仅 live 路径携带）+ 前端断链校验主动 resync + 1s 周期全帧对账（A1+A2）；mid-stream error/exit 状态行直写后强制 resync（C1，直写绕过有序队列的滚动副作用无重画补偿——同一不变式的另一处违反）。故障注入实证：第二条连接偷基线期间探针视角 seq 断链 90 处，前端 3s 内发 resync 4 次（节流限频），画面最终收敛无残留（计划：`2026-09-08-pty-incremental-sync-hardening.md`）。
- 2026-09-09 A1 周期全帧上线后新症状：打字间歇/状态栏更新时光标闪跳终端右下角。根因是**兜底机制自身的衍生缺陷**：渲染 rows 必然 CUP（全帧逐行 CUP 到底行），渲染后 xterm 光标停在重画终点；而 cursor 字段被后端去重（基线 = 上次编码值），「光标未变」的帧省略该字段，污染得不到纠正直到下一次光标实际变化。教训：**字段省略（去重）优化的基线必须是客户端可观测状态，而非上次编码值**——凡渲染动作有副作用（移动光标/改样式），省略字段就必须配恢复，或改为「带副作用的帧不省略该字段」。修复：前端 applyCursor 按 Terminal 实例学习最近一次显式 cursor，帧缺 cursor 且渲染了行时回写（viewport 历史窗口帧不学习）。

## 模式 9：同一字节流双终端模拟器消费时，查询序列必然重复应答（迟到应答透传回显）

**终端-双消费者应答**：架构里同时存在两个终端模拟器（如服务端 VT grid + 前端 xterm.js）消费同一份 PTY 输出时，查询类序列（设备属性 DA、光标位置 CPR、颜色 OSC 等）会被**各自应答**；发起方（tmux/应用）在等待窗口内只消费一份应答，**迟到的重复应答不被解析、直接透传给 shell，经 PTY echo 回显成可见残片**。判定签名：屏幕冒出形如 `1;2c` 的短串（= xterm.js DA1 应答 `\x1b[?1;2c` 去掉不可见 ESC 后的残片），且随会话切换/重连成串出现——每次重连触发一次发起方探测 + 一次泄漏。规律有二：① **应答权必须唯一**——凡后端持有 VT 模拟器的架构，查询应答归后端，前端对查询的自动应答要在输入回路上按「锚定整串白名单」过滤（白名单之外必须放行鼠标上报与后端未实现的探测，否则丢合法输入/探测降级）；② 屏幕上出现「疑似输入残片」时，先对照 xterm.js 的自动应答清单（`triggerDataEvent` 调用点）定罪，再怀疑输入路径泄漏——库的自动应答走 onData，与用户输入不可区分。

**弯路**：交接期把 `1;2c` 归因为「SGR bold+dim 残留 + tmux new-window 命令经未追踪路径打进去」，沿键盘 handler 闭包、会话切换 reset 的方向修了两轮未收敛——方向本身错了：那些修复覆盖的路径根本不产生这个串。教训：残片字符先「溯源到它唯一可能的一手来源」（DA 应答格式精确匹配 `1;2c`），而不是从「哪段代码可能写屏」反推。

**案例证据**：
- 2026-08-28 pty 会话多次切换后冒出 `1;2c1;2c1;2c`（每次切换泄漏一次）。根因：tmux attach 在连接初期裸字节窗口期发 DA1 查询，前端 xterm.js 经 onData 自动应答回写 PTY，与后端 VT 已回写的应答形成重复。修复：pty 会话 onData 按白名单过滤 xterm.js 全部自动应答（tmux/外部会话不过滤——那里前端是唯一终端模拟器）。
- 2026-09-06 pty 会话在 Ink 系 TUI 输入框内粘贴多行文本被逐行当 Enter 提交。同家族第二例：受影响的不是查询应答而是**输入语义模式**——TUI 发的 `?2004h`（bracketed paste）被 cell_frame 架构吞掉（raw 流只排干不转发），前端 xterm 的 `bracketedPasteMode` 恒 false，桌面 Ctrl+V 不加 `200~/201~` 包装裸发；移动端长按粘贴更是完全绕过 xterm 直发，连换行转换都没有。修复：模式经 cell_frame 的 `bracketed_paste` 字段中继（所有帧携带），前端与 `term.modes.bracketedPasteMode` 不一致时写回序列同步；移动端改走 xterm `paste()`（`docs/dev/plans/archive/2026-09-06-pty-bracketed-paste-relay.md`）。教训升级：**双模拟器架构下，凡影响输入语义的模式状态都必须后端中继**，否则前端侧的输入预处理（粘贴包装/换行转换）按错误前提工作。

## 模式 10：拉模型视口必须配刷新触发源与逃生口，「相对偏移」在增长序列上不稳定

**终端-拉模型刷新**：「客户端请求偏移 → 服务端返回窗口」的拉模型（历史视口、分页、无限列表），若**只在用户操作时请求一次**，服务端数据持续变化时客户端会永久停在请求那一刻的快照——它既不刷新也不报错，用户看到的是一份「看起来正常但永不更新的屏幕」。判定签名：**切换会话/重连后立刻正常**（重建走初始化路径拿到了真相源），而同一连接内怎么等都不动。修法三件套缺一不可：① 服务端在数据变化时给出**信号**（帧内带状态版本号/行数，或独立的变更通知），客户端据此重拉；② 客户端保留**逃生口**——真实终端语义是「任何键盘输入都把视口拉回活动行」，没有这条，用户在全屏程序里滚一下就再也回不到实时画面；③ 用**「本条消息是否真的有变化」**过滤刷新（周期 tick 帧多数是空帧），否则空闲场景也会持续空转请求。

**终端-相对偏移不是稳定标识（位置型锚点 → 内容型锚点）**：在只增、且可能环形淘汰的
数据集（终端 scrollback、日志环、分页列表）上做「保持看到同一批项」，**相对偏移
（距底部 N 行）与绝对索引（距顶部 N 行）都不是稳定标识**：前者在数据集增长时指向的
内容持续变新；后者在淘汰（环形回绕）时内容整体前移。于是「锚点换算」的正确归属是
**持有数据集真相源的一侧**——它能在请求到达的同一时刻用最新状态换算，而消费端拿到的
状态副本天然滞后一个采样周期（实测滞后 33ms + rAF 16ms，每轮漂移 ~0.5 行，20 秒累计
109 行）。当连真相源一侧都无法用数字表达位移时（本例：历史饱和后 `history_size`
恒定，无法推出「期间新产出了几行」），**改用内容指纹锚定**：记住锚定项的指纹，每次
请求由近及远在**有界窗口**内搜回它当前的位置。指纹失配（内容被淘汰/重写/reflow）时
退回偏移定位，降级而不失效。**判定签名**：视图「缓慢滑动」而非静止——先量滑动速率与
输出速率的比值，比值恒定即锚点换算在漏量；再确认漏的是「位置量」还是「帧」。

**弯路**：第一轮把「视图滑动」当成渲染或丢帧问题查，花在帧内容、xterm 渲染、alt-screen
粘连、僵尸观察者上的时间全部落空——那些路径实测全部干净（帧内行号连续、渲染与帧逐行
一致）。真正的分水岭是「后端能否用数字表达位移」这一问：不能，就必须换锚定方式，继续
在位置换算上打补丁（比如把采样频率调高）只能缩小漂移、不能归零。另一条弯路是先选了
「后端新增已输出行数计数器（包装 vte Handler）」，后证实 `alacritty_terminal::Term::input()`
在自动折行时**内部调用 `self.wrapline()`**，不经过 Handler 包装层 → 长行折行（agent 输出
最主要的滚屏来源）根本计数不到。**给模拟器/解析器做计数前，先确认目标操作是否真的
经过那层钩子。**

**案例证据**：
- 2026-08-30 pty 终端上翻后画面冻结、新输出完全不可见（在 `top` 里滚一下，之后压测 12 秒屏幕纹丝不动，只有切换会话才恢复）。根因：窗口帧只在滚轮时请求一次，viewport 模式下实时帧被丢弃且无人重拉。修复：所有 cell_frame 携带 `history_size`，前端按绝对锚点重算 y 并重拉；键盘输入自动回底；有未查看新输出时显示回底提示条。
- 2026-09-03 同家族第二次：上条修复后视图仍滑（未饱和时达输出速率 28%，饱和后 100%）。根因：`y` 为距底偏移，历史饱和后 `history_size` 无法表达期间新增行数，且前端换算用的是滞后一帧的副本。修复：请求带窗口首行内容指纹，后端在有界半径（512 行）内由近及远重定位并按实际位置出窗口；实测未饱和与饱和两种场景下锚定内容恒定 10 秒，锚定行被淘汰后才按真实终端语义随淘汰滑动（计划：`2026-09-03-pty-viewport-fingerprint-anchor.md`）。

**终端-前提是实测的**：`全屏 TUI 程序 = 用 alt-screen` 是**错误前提**。实测 procps-ng `top` 在本机真实 PTY 里根本不发 `?1049h`（只发 `ESC[?1h ESC= ESC[?25l ESC[H ESC[2J`，直接在主屏绘制），`vim`/`htop` 同样不发，而 `less`/`tput smcup` 会发。凡由「alt-screen 事件」驱动的逻辑（禁用滚轮接管、切换缓冲区、清屏），**必须抓目标程序的原始字节确认它真的发该序列**，不能靠「它是全屏程序/它用了 ncurses」推断——terminfo 有 `smcup` 不等于该程序会调用它。附带结论：这类程序每轮刷新都把内容推进 scrollback，「历史里出现 TUI 残留画面」是预期行为而非清屏不彻底。

**适用**：一切「请求-响应」拉模型的视口/分页；一切依赖「程序类别 → 行为」推断的终端特性分支。

**弯路**：第一轮复现用 `for i in $(seq 1 N); do echo …; done` 当「持续输出源」，上翻后看到内容不变就定罪为冻结——**错的**：那个循环几百毫秒就跑完了，内容不变是因为后端真的没输出。第二轮仍栽在同一处：3 秒内收到 97 帧 cell_frame、其中**含变化行 0 帧**，这才暴露「后端已停」。教训：验证「是否冻结」必须先证明**后端仍在产生变化**，用帧探针统计「含变化行的帧数」；持续输出源要选**永不结束的**（`top`），不要选跑得完的压测。

**案例证据**：
- 2026-08-30 pty 终端上翻后画面冻结、新输出完全不可见（在 `top` 里滚一下，之后压测 12 秒屏幕纹丝不动，只有切换会话才恢复）。根因：窗口帧只在滚轮时请求一次，viewport 模式下实时帧被丢弃且无人重拉。修复：所有 cell_frame 携带 `history_size`，前端按绝对锚点重算 y 并重拉；键盘输入自动回底；有未查看新输出时显示回底提示条。

## 模式 11：回放的历史是字节快照，恢复前必须补齐尾部语义边界

**终端-回放边界**：ANSI 历史的落盘/回放容易只做「字节搬运」，但**快照可以在
任意字节处截断**——它不是一个语义完整的单元。典型是 shell 打印 PS1 后等待
输入（不带换行）时会话消亡（后端重启、进程被杀、容器回收），历史就停在半行
`…$ `。重建回放后光标停在该半行末尾，**新会话的输出直接接在后面**，与残留
内容拼成一个语义单元（`$ $ $` 堆成一行，视觉上「屏幕只剩一行」）。

判定签名：**每重建一次，症状叠加一层**（提示符越来越多），而不是一次性错乱。
累加本身就是证据——说明残留被反复复用，而非随机损坏。

修法：回放后按语义补齐尾部边界。三类边界同源，缺一不可：① **半行**补换行
（已以 `\n` 结尾不补，只缺 LF 的 `\r` 结尾补 `\n`——多补一个 CR 会擦掉行首
内容）；② **截断的多字节字符**按 UTF-8 边界回退（环形窗口按字节淘汰必然切得
到）；③ **未闭合的转义序列**同样要丢弃尾段，否则新输出被当成序列参数吃掉。

**适用**：一切「持久化历史 → 重建回放 → 继续追加」的链路（终端会话恢复、日志
续写、断点续传）；设计回放协议时先问「快照的尾部边界由谁定义」。

**弯路**：先在重连/尺寸抖动方向查了两轮——后端直连重连、刷新页面重连、强制
blur 断连重连、以及 88x48→80x24→88x48、2x1、1000x48 的极端尺寸抖动，全部
干净（alacritty 的 reflow 对硬换行是忠实的，不会把多行并成一行）。真正的
触发条件不是「重连」而是**会话进程真的没了**。教训：症状报「重连后出现」时，
先区分是「连接重建」还是「会话重建」——后者才会走回放路径。另外，复现「进程
消亡」不能用会话内 `kill -9 $$`（那样历史的最后一行是命令回显、以换行结尾，
反而测不出来），要从宿主按 pid 杀，让历史停在半行。

## 模式 12：双模拟器镜像架构中，行数契约失守 = 屏幕底部区域永久冻结

**终端-尺寸契约**：服务端 VT grid 与前端 xterm 各持一份屏幕状态，靠「帧按绝对行覆盖 `0..height-1` + resize 消息同步行数」维持镜像。该契约有两个失守口：① 前端 resize 事件在 WS 未 open 时被 readyState 门禁**静默丢弃**，连接初期容器布局未稳（侧栏动画/字体加载）时最后一次 fit 落入该窗口即分叉；② 重连/切换时序竞态同理。分叉后帧只覆盖顶部 `height` 行，xterm 底部多余的行**不被任何帧触碰**、停留旧内容——症状：TUI 画在输入行上方、底部垫陈旧画面，且不会自愈（无新尺寸事件就没有 resize 消息）。修法三层缺一不可：WS open 时无条件补发当前尺寸（后端同尺寸幂等）；帧消费侧检测帧 `height/width` 与本端 `rows/cols` 不符即补发 resize（任何分叉 ~1 帧内自愈）；后端 resize 作废 diff 基线保证收敛。

**判定签名**：陈旧内容出现在屏幕**底部固定区域**、行数 = xterm.rows − 帧 height；切换会话/重连（重置 xterm）后暂时正常。排查第一步是比对「帧 height」与「xterm rows」这两个数字，而不是逐帧比对内容。

**弯路**：用「内容止于第 N 行」反推后端行数——但 TUI 自身有预留行行为（Ink 启动时写 4 个 LF 再 CUU 回位，底部留 5-8 行空白是**正常形态**），静态截图无法据此定罪分叉。正确顺序：先拿参考模拟器（tmux capture-pane）跑同一字节流对照、排除 TUI 自身行为与后端 grid，再比对双端行数。

**案例证据**：
- 2026-09-04 pty 会话在屏底启动 codebuddy，画面「TUI 在输入行上方、底部垫上次会话的退出文本与提示符」。tmux 对照排除 TUI 自身行为与后端 grid（alacritty 处理正确）后，定位为 xterm 与后端行数分叉（帧尺寸自愈验证：外部强缩后端到 20 行，浏览器 1 帧内拉回 48）。修复：open 补发尺寸 + 帧尺寸自愈（`useTerminal.ts`）+ y=0 跳过指纹重定位（见模式 10 勘误）。

**终端-列宽契约**：几何契约不止行数——**每个字符占几列**也是双端各自独立计算的。cell_frame 编码跳过宽字符占位 cell（只发主字符），前端按自己的宽度表重放列宽；xterm.js 默认宽度表停留在 Unicode 6（⬛⬜🟥🟩 等方块 emoji 在 Unicode 9-12 才定为 Wide，默认按 1 列），而后端 alacritty 的 unicode-width 按 Unicode 15 给 2 列——每个此类字符偏移 1 列，**从第一个宽字符起逐字符累积**，「像素方格」logo（方块 emoji 构成）整体压扁错位。判定签名：ASCII 区域完好、错位从特定字符开始且越靠右越歪；同一内容在 tmux（或参考模拟器）下正常。修法：两端宽度表同源——前端加载 Unicode11Addon 并 `term.unicode.activeVersion = '11'`（proposed API，须 `allowProposedApi: true`），在首帧写入前生效。注意此契约只在「帧编码跳过占位 cell」的架构下成立：若帧按 cell 逐列传输则宽度表差异被占位 cell 掩盖，切换传输格式时契约责任随之转移。

**案例证据（续）**：
- 2026-09-09 pty 会话跑像素方块 logo（⬛🟥 构成）整体压扁、后续内容水平错位。headless 探针实证：xterm 默认表下 `⬛` 写入 buffer 占 1 列（X 落 col 1），unicode11 激活后占 2 列（X 落 col 2），与后端 grid 对齐。修复：`useTerminal.ts` 加载 Unicode11Addon（`@xterm/addon-unicode11@0.9.0`，与 xterm 6.0 同批发布）；回归测试 `useTerminal.unicode11.test.ts`（真实 xterm 断言 ⬛🟥=2 列、▀▄█ 与 CJK 不回归）。

**终端-cell 语义契约**：几何之外，**cell 内容本身的渲染语义**也须两端一致——最典型的是 TAB：alacritty 把 TUI 输出的 `\t` 存为普通 grid cell（渲染语义 = 1 列空白，无论该 cell 落在哪一列）；而 xterm.js 把写入的 `\t` 解释为 HT 跳位（跳到 8 列对齐的 tab stop，宽度 0~7 列不定）。cell_frame 编码原样透出 `\t` 后，同一 cell 序列在两端的渲染列布局不同。判定签名：**同一行初画正确、后续被 TUI 重写后该行整体右移 + 行尾内容 wrap 掉到下一行（两行变形）**——触发条件是该行重写时带了 `\t` 缩进（如 TUI 延迟填充状态数据）。修法：编码侧归一化（`push_cell_text`/`render_screen` 把 TAB cell 输出为空格），维持「前端按 cell 序列 1:1 重放 = 后端 grid 视角」的不变式；单测 `tab_cells_are_normalized_to_spaces_in_frame_and_screen` 守护两条编码路径。

**案例证据（续）**：

**模式 10 追补（同次排查）——回底校准请求不得做指纹重定位**：y=0 的语义是「回底看 live 屏」，但 live 屏顶行（空行/提示符行）与历史行同内容是常态，`relocate_anchor` 会把 y=0 的回底帧吸附成历史窗口，前端 `currentY` 被带偏后恢复定时器的 `currentY == 0` 条件失效 → 卡在 viewport 模式。当时的修正（y=0 跳过重定位，恒服务 live 屏）已于 2026-09-12 被下述机制**整体承接**（y=0 清锚），所指回归测试随指纹机制一并删除。
