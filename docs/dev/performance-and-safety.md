# 性能与安全指导

> 目标：防止「本地开发测不出来、真实负载一触即爆」的性能缺陷与安全漏洞进入代码库。
>
> **触发条件（何时必读）**：任何涉及以下内容的代码改动——
> 数据累积/缓冲、持久化写入策略、外部输入（agent 通知 / 用户输入 / 文件内容）、
> 命令执行、跨层数据传输（WS / HTTP / DB）、吞吐量或延迟敏感路径。
>
> 每个红线都对应一次真实事故或踩坑记录，见文末「案例索引」。

---

## 一、性能红线

### P1 无界累积禁止（buffer bounds = invariant）

**任何持续 `push` / `append` / `collect` 进内存、DB 列、通道、消息的累积结构，必须有显式上限、超限策略和守住它的单测。** 三个问题写代码时必须回答：

1. **上限是什么？** 帧数 / 字节数 / 条目数，提取为命名常量（如 `MAX_FRAMES = 2000`），禁魔法数字。**上限维度必须匹配真实的增长维度**：写下 `MAX_X = N` 时回答「N × 单条最大 = ?」——答不出来（单条大小由外部实现决定）就说明只限条目数等于没限，必须再补一条字节上限（见案例 2）。
2. **超限怎么办？** 丢弃最旧（窗口）、截断、或拒绝新数据——必须明确并落注释。
3. **用什么测试守住？** 构造超过上限的输入，断言累积结构长度恰为上限（回归防护）。

「累积结构只活一个 turn / 一个请求」这类**注释描述的意图不算上限**——意图不兑现就是事故现场（见案例 1）。

### P2 防抖写 ≠ 增量写：警惕 O(n²)

**防抖/节流只解决「写得多频繁」，不解决「单次写多大」。** 若写入策略是「周期快照整个增长中的缓冲区，全量重序列化 + 覆盖写」，缓冲区无界时总成本必然平方级：

- 每次快照 O(n)，n 随时间增长，持续运行总成本 O(n²)。
- 三处同爆：CPU（序列化）、内存（缓冲 + 临时字符串）、存储（DB/文件膨胀）。

**判定**：快照对象有界 → 全量快照可接受；快照对象无界 → 要么增量写（只写新增），要么先限界（P1）。

### P3 事件日志当状态持久化必须配套 retention policy

事件日志（event log）与状态（state）是两种东西。拿原始事件当持久化单元（重放时再还原）时，**必须有滚动/截断策略**，否则就是无界日志。若事件日志只服务于「最近状态的恢复」，只保留最近窗口即可，完整状态交给有界快照或增量合并。

### P4 外部输入速率不受控，入口设流量防线

上游的推送速率、单帧大小、总量**不由我们决定**（agent 子进程、上游服务、用户脚本）。对第三方产生的数据量：

- 入口处设上限（帧率 / 单条大小 / 累积总量），而非假设「它们会温和地输出」。
- 这是 AGENTS.md §8「多实现兼容性」的反向延伸：不只考虑「某些实现可能不提供某能力」，还要考虑「某些实现可能提供超高频、超大量的数据」。

### P5 容量缺陷全链路传导

一个无界数据源有多少出口（DB 列 / WS 帧 / hydrate / 重放 / 导出），每一个都会被放大相同的量级。修一个出口不解决其他出口；枚举全部出口逐一评估，或在源头限界一次解决全部。

### P6 真实负载验证不能省

容量/吞吐问题在「短对话 × 本机」下永远不暴露。以下改动必须用长任务 / 高频输入 / 大数据量验证：

- 会话引擎、流式链路、持久化策略
- 任何新增的累积结构与写入策略
- 手动回归用例可参考 `docs/reference/user-testing.md`

## 二、安全红线

### S1 一切外部输入必须 sanitize

| 输入类型 | 必须做什么 | 项目现有参照 |
|---|---|---|
| 文件/目录路径 | 越界校验（拒绝 `..` / 绝对路径逃逸） | `src/fs/mod.rs::sanitize_path`（ws/acp.rs 的 `resolve_at_references` 已用） |
| 命令与参数 | 用参数数组 `Command::new(...).args(...)`，**禁 shell 字符串拼接**（防命令注入） | `src/acp/terminal.rs::handle_create` |
| HTML / 富文本 | 按纯文本渲染或转义，禁止直接 `dangerouslySetInnerHTML` 外部内容 | 前端 Markdown 组件（react-markdown 默认转义） |
| 数值/枚举 | 显式类型化 + 白名单校验，不接受任意字符串隐式转义 | `RuntimeKind` / `agent_kind` 枚举 |

**规则**：凡来自网络、子进程、文件、用户输入的数据进入路径解析、命令构造、HTML 渲染、SQL 前，先 sanitize 或走白名单。

### S2 禁止吞异常掩盖症状

`try-catch` / `Result::ok()` / 空 catch 吞掉错误会让缺陷变成「静默数据损坏」或「永久卡死」。错误要么上抛到有意义的边界，要么记日志 + 显式降级，**不掩盖根因**（呼应 AGENTS.md §5 缺陷修复）。

### S3 敏感数据不落日志、不落库明文

token、密码、密钥、API key：
- 不进入 `tracing` 日志（结构化字段需脱敏）。
- 不落库明文（参考 `jwt_secret` 独立文件 + 权限 600 的做法）。
- 调试日志打印请求体/响应体前，确认不含凭据。

### S4 权限最小暴露

- 新 API 端点 / WebSocket：确认是否需要鉴权，勿默认匿名可访问（历史教训：鉴权曾实现后从未接入路由，见 `docs/reference/auth-not-enforced.md`，当前已修复）。
- 文件系统访问：以 session 的 workspace_path 为根，任何越界访问必须拒绝（S1 路径 sanitize）。
- 后台命令：agent 的 `terminal/create` 等能力按需开放，不做多余暴露。

### S5 鉴权/授权状态必须显式校验

「名义上有鉴权、实际匿名可访问」比「没有鉴权」更危险（误以为安全）。启用任何安全机制时验证它**真正挂在链路上**：grep 确认 extractor/中间件被路由引用，而非只有定义处。

## 三、提交前自查清单

**性能：**
- [ ] 每个累积结构有命名上限 + 超限策略 + 单测？（P1）
- [ ] 写入是增量还是全量快照？快照对象有界吗？（P2/P3）
- [ ] 外部输入速率有防线吗？（P4）
- [ ] 无界数据源的所有出口都评估过量级？（P5）

**安全：**
- [ ] 路径 / 命令 / HTML / SQL 的外部输入都 sanitize 或白名单？（S1）
- [ ] 有没有 try-catch 吞错误掩盖根因？（S2）
- [ ] 敏感数据可能进日志或明文入库吗？（S3）
- [ ] 新端点 / WS 鉴权了吗？（S4/S5）
