# Plan 检查点（写作参考，非强制结构）

> 用途：在 `docs/dev/plans/` 下撰写实施/设计计划时的**检查点清单**与参考骨架。
> 触发条件：准备就某个功能、重构或质量专项撰写计划文档前，**建议过一遍**本清单。
> 维护触发：检查点需要调整（新增/精简维度）时更新本文件。
> **定位说明**：本文件是**检查点（checklist）**而非**强制模板**。它不是"计划必须长这样"，而是"一份经得起评审的计划，应当能回答下面这些维度的问题"。允许按任务性质裁剪、合并、重排区块——但不要为了凑结构而注水；若某个维度不适用，显式写一句"不适用"也比硬凑强。

---

## 0. 命名与存放

- 文件名：`YYYY-MM-DD-<kebab-subject>.md`（日期为计划创建日）。
- 存放：`docs/dev/plans/`（不被 sync-main 黑名单排除的开发计划）；长期跟踪项放 `docs/dev/plans/backlog/`。
- 状态字段取值：`设计稿` / `进行中` / `已实施` / `已归档`。

## 检查点清单

下列每一项是一个**应被回答的问题**。在文中以任意合适的形式覆盖即可，不要求机械对应小节编号。

| # | 检查点 | 关键问题 | 参考 |
|---|--------|----------|------|
| 1 | **元信息** | 状态、触发条件、关联文档是否写清，便于检索与追溯？ | 各 plan 头部引用块 |
| 2 | **背景驱动** | 是否基于审查/审计而非拍脑袋？现状、问题清单、严重度、根因是否清楚？ | quality-gates 审计表；mobile 问题清单 |
| 3 | **范围分级** | 是否用 P0/P1/P2 区分优先级与预估？ | 各 plan §2 |
| 4 | **排除项** | 明确不做什么？是否给了产品定位/复杂度理由（奥卡姆剃刀）？ | git-panel 排除清单 |
| 5 | **设计决策** | 每个关键决策是否固化了「决策 + 理由 + 否决项 + 翻盘条件」？ | git-panel ADR；auth 决策表 |
| 6 | **多实现差异** | 涉及多客户端/协议时，是否显式列出差异与降级兜底（AGENTS §8）？ | acp 风险表；git-panel ADR-4 |
| 7 | **实施分期** | 是否按依赖顺序分阶段？改动文件/产出是否列清？依赖关系是否标注？ | auth §4.7；acp Phase 表 |
| 8 | **验收标准** | 是否有可勾选的验证清单，含后端/前端、边界 case、质量门禁（clippy/tsc 零新增）？ | 各 plan 验证清单 |
| 9 | **风险与降级** | 主要风险是否识别，且每项有缓解/兜底路径而非"待观察"？ | acp 风险表 |
| 10 | **文档闭环** | 实施后需更新的文档 + CHANGELOG 是否映射？ | auth §6；quality-gates §6 |
| 11 | **术语表** | 复杂计划是否统一了多人接手的语言？ | git-panel Glossary |

> 并非每个计划都需要 11 项全亮。一个 30 分钟的热修计划，覆盖 1/2/7/8 即可；一个跨多模块的设计，5/6 是重点。判断权在作者。

## 参考骨架（可裁剪，非必抄）

下面是一份常见结构，**仅作起点**。实际写时按任务性质增删：

```markdown
# <计划标题>

> 状态：设计稿（YYYY-MM-DD）
> 触发条件：<...>
> 关联：<...>

## 背景
- 现状摘要 / 问题清单（含严重度）/ 风险与根因

## 范围与优先级
- P0 / P1 / P2（目标 | 要点 | 预估）
- 不纳入范围（含理由）

## 设计决策 / ADR
- 决策 / 理由 / 否决项 / 翻盘条件
- 多实现差异与降级（如适用）

## 实施分期
- Phase 1 ... / Phase 2 ...（产出 | 改动文件 | 依赖）

## 验收标准 / 验证清单
- [ ] 后端 ...
- [ ] 前端 ...
- [ ] 边界与降级 ...

## 风险与文档闭环（如适用）
- 风险表 / 需更新的文档 + CHANGELOG
```

## 写作纪律（比结构更重要）

1. **不注水**：结构服务于思考。若某区块无实质内容，写"不适用"或删掉，不要填充空话。
2. **决策留痕**：最有价值的不是"做什么"，而是"放弃了什么、为何"——否决项与翻盘条件务必写。
3. **计划≠事实**：实施中发现偏差，就地用「勘误」块记录（参照 quality-gates 的 4 处偏差修正），而非默默改掉或假装计划一直正确。
4. **对齐工程准则**：范围分级呼应奥卡姆剃刀；多实现差异呼应 AGENTS §8；根因呼应 AGENTS 第 5 条。
