## 背景

`docs/dev/debug-guide.md` 的「体积纪律」规定**每个领域文件 ≤30KB，超限拆出新的领域文件**。当前各领域文件体积：

| 文件 | 体积 | 状态 |
|------|------|------|
| `terminal-pty.md` | **35.8KB** | ❌ 超限（本次追加「订阅前的事件不可见」前已 34.7KB） |
| `platform-protocol.md` | 16.2KB | 正常 |
| `resource-lifecycle.md` | 15.4KB | 正常 |
| `frontend-react.md` | 12.2KB | 正常 |
| `layout-visual.md` | 11.7KB | 正常 |
| `investigation.md` | 10.9KB | 正常 |
| `async-race.md` | 5.3KB | 正常 |
| `unresolved.md` | 3.2KB | 正常 |

超限的成因不是单条记录臃肿（最大单条 4.2KB），而是**该文件承载了 4 类症状领域**（19 条 bold 条目 / 12 个 `## 模式 N`），远超其他领域文件的单一职责。这也是「领域文件 = 渐进式披露的加载单元」这一机制的直接损耗：查「ptx 尺寸契约」的读者要被 4.7KB 的复用器语义与 18KB 的帧流记录一并加载。

本次会话**不推进拆分**，理由是净收益 < 一次搬移重构的风险：本次仅新增 1.1KB，而拆分要搬移 19 条条目 + 重排领域索引 + 更新全仓引用，回归面（条目丢失、引用断裂）大于收益。

## 核心症结

**按行数切会把同一症状家族切碎**。上述 12 个模式实际聚成 4 个症状领域，每个都有独立的「改什么代码前必读」触发条件：

| 领域 | 覆盖模式 | 触发条件（读者何时来查） | 估体量 |
|------|---------|------------------------|--------|
| A 复用器与进程 | 1、2、3、4、新增订阅 | 改 tmux/psmux 交互、命令构造、pty 生命周期、控制模式订阅 | ~4.7KB |
| B 帧流与丢帧 | 6、7、8 | 改 diff 流编码、帧序号、全帧对账、推送节流、聚合 | ~9.9KB |
| C 历史与视口 | 10、11 | 改历史视口拉模型、回放落盘/补屏、锚点策略 | ~8.3KB |
| D 镜像渲染契约 | 5、9、12 | 改 xterm 渲染、尺寸/cell/宽度契约、双模拟器应答权 | ~11.4KB |

## 设计决策（ADR）

**D1 · 切分轴：按症状领域（A/B/C/D），不按行数或条目序号**
- 理由：领域文件的唯一职责是「症状 → 规律」的检索入口，切分必须让索引关键词与文件一一对应；按行数切会让同一家族跨文件。
- 否决项：按「前半 / 后半」对半切（检索性最差）；按「后端 / 前端」切（模式 6-8 与 12 都横跨两端，会制造跨文件家族）。
- 翻盘条件：若实施时发现某两条目按领域归属存在争议且无法判定，允许该条目留在**其触发条件更常命中的一侧**，并在另一侧留一行交叉引用（不建双份真相源）。

**D2 · 拆成几份：推荐 3 份，备选 4 份，否决 2 份**
- 推荐（3 份）：`A+B`「复用器与帧流」（14.6KB）｜ `C`「历史与视口」（8.3KB）｜ `D`「镜像渲染契约」（11.4KB）——三者的「改什么代码前必读」触发面互不重叠，各自 ≤15KB，离 30KB 上限保留约 2× 增长余量；索引 3 行。
- 备选（4 份）：A / B / C / D 各自独立（4.7 / 9.9 / 8.3 / 11.4KB）。检索精度最高，代价是索引多一行、条目间交叉引用增多（模式 6-8 与模式 10-12 之间存在同族引用）。
- 否决（2 份）：按「生产/传输侧」`A+B+C`（23KB）+「渲染侧」`D`（11.4KB）——23KB 离上限只剩 7KB，一轮追加即回到超限，没有留增长余量。
- 否决：不拆（继续超限，违体积纪律）；拆成 7 份（单模式成文件，索引膨胀且同族条目被迫跨文件跳转）。
- 翻转判据：若 `A+B` 在 3 个月内超过 20KB，按备选 4 份把 B（帧流与丢帧）拆出。

**D3 · 编号策略：保留原「模式 N」全局编号，不重排**
- 理由：`docs/dev/plans/archive/2026-09-12-pty-viewport-stateful-anchor.md` 等文档与本文件内部存在按编号的交叉引用（如「模式 10」「模式 12」），重编号会静默改变这些引用的指向。
- 代价：拆分后单个文件出现不连续编号——以文件头一行「本文件包含模式 X/Y/Z（原 terminal-pty.md）」消解。
- 翻盘条件：若日后统一重编号，必须同批更新全部引用（`grep -rn "模式 1[0-2]\|模式 [1-9]" docs/` 核对）。

**D4 · 结构统一：无编号 bold 段不强行升格为 `## 模式 N`**
- 现状：模式 8/10/12 内部各有 1~2 条无编号 bold 段（同家族的追加记录，符合「家族合并纪律：追加案例不新开条目」）。拆分只做搬移，**不改写内容、不补编号**。
- 否决项：借拆分之机顺带重写条目（违反「拆分只搬移」原则，会引入无法评审的语义漂移）。

**不适用**：§6 多实现差异（本文档是文档重构，不涉及协议实现）；§11 术语表（术语已由各条目自带）。

## 实施分期（触发后执行）

- **Phase 1 · 快照与清单**：导出当前 19 条 bold 条目的标题清单与 12 个 `## 模式 N` 的映射表（作为零丢失基线）；收集全部引用点（实测当前 7 处：`debug-guide.md` 索引、`platform-protocol.md`、`2026-09-12-pty-viewport-stateful-anchor.md` 及 4 份归档计划）。
- **Phase 2 · 搬移**：按 D1/D2 落位，新建文件头写「本文件包含模式 X/Y/Z（原 terminal-pty.md 拆分）」；保留 `terminal-pty.md` 作为薄入口或直接改名（取决于 D2 结果），被拆出条目原位置留一行指向新文件的引用。
- **Phase 3 · 索引改造**：`debug-guide.md` 领域索引把 1 行拆成对应多行，**每行关键词必须含该文件全部条目的症状词**（索引行是唯一入口，缺词即检索不到）；跑 `./scripts/check-doc-index.sh`。
- **Phase 4 · 引用修正与复核**：更新 Phase 1 收集的引用点；按验收清单核对。

## 验收标准

- [ ] 每个新文件 ≤30KB（目标 ≤20KB 留增长余量）
- [ ] 条目零丢失：拆分后各文件 `grep -c '^\*\*终端'` 之和 = **19**，且标题逐条比对与 Phase 1 清单一致
- [ ] 编号引用未失效：`grep -rn "模式 [0-9]" docs/` 的命中仍指向同一规律
- [ ] `./scripts/check-doc-index.sh` 通过；领域索引每行关键词覆盖其文件全部症状词
- [ ] 全仓引用点（`docs/`、`AGENTS.md`、`CHANGELOG.md`、`scripts/`）无指向已移动内容的失效指针
- [ ] 不改写内容：`git diff` 中除搬移与文件头/交叉引用外无正文语义改动
- [ ] 不涉及 CHANGELOG（纯文档结构重整，按 CHANGELOG 约定不写条目）

## 风险与缓解

| 风险 | 缓解 |
|------|------|
| 搬移中丢条目（历史上 PROGRESS.md 断链悬空 3 个月未被发现） | Phase 1 先固化清单，Phase 4 用计数 + 逐条比对核对，不靠肉眼 |
| 领域索引关键词漏词 → 渐进式披露失效（拆了文件但查不到） | 索引行按「文件内全部条目的症状词」重写，而非只写文件主题 |
| 交叉引用断裂 | Phase 1 一次性 grep 全仓引用点，Phase 4 复核 |
| 拆分后读者仍需跨文件跳转（家族被切开） | D1 的翻盘条件：争议条目留在更常命中的一侧 + 另一侧留引用 |

## 推进触发条件

满足任一条即推进（不设时间表）：

1. 下一次需要往 `terminal-pty.md` 写入新规律时（写之前先拆，避免在超限文件上继续加）；

3. 该文件超过 **40KB**（硬红线，届时即使无其他触发也必须拆）。
