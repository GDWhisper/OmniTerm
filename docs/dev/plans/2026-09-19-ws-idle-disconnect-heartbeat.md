# WS 空闲断连归因与心跳方案

> 状态：设计稿（2026-09-19）
> 触发条件：修改 `src/ws/terminal.rs`（`ClientControl::Ping` / `ServerControl::Pong`）、`src/ws/acp.rs`、`src/engine/*/terminal_ws.rs` 的 WS 读写循环、`frontend/src/hooks/useAcpChat.ts` / `useTerminal.ts` 的连接保活与重连、或调整 cloudflared / 反代超时前**必读**
> 关联：`docs/architecture/frontend.md`「终端自动重连引擎」小节（既有自愈策略与退避语义，本计划只解决「为什么会断」，不重复设计重连）、`docs/dev/debug-patterns/terminal-pty.md`（轮询推送时延下界、拉模型逃生口）
> 来源：2026-09-19 用户报告「公网 CF 访问正式版，聚焦使用终端会短时间内自动断连，频繁需要手动点重连」；同日会话 `codebuddy_0919-0946` 排查未闭环。证据取自 `~/.omniterm/omniterm.log`（正式版 v0.2.22，PID 792178）与 `/etc/cloudflared/config.yml`

## 背景

### 现象与已测数据

- **ACP WS 在「已释放、无任何流量」状态下，连接寿命稳定落在 125.2–125.4s**：`02:38:15 / 02:42:16 / 02:44:23 / 03:04:42 / 03:09:05 / 03:11:39 / 03:13:46 / 03:18:34 / 03:20:48 / 03:22:55 / 03:25:02`（重置）← 每次重连后约 125s。重连延迟不等（1.2s ~ 18min，与页面可见性/退避有关）。
- 断开形态全部是 `ResetWithoutClosingHandshake`（服务端读到 TCP 重置，非 WS 关闭握手）；同一条链路会立刻重连（前端自动重连已生效）。
- **turn 进行中（有 session/update 流量）时寿命变长但不归零**：turn 2 内三次为 463s / 125.3s / 253.1s——125s 档在「有流量」时仍出现，说明**不能简单归因于空闲**。
- **终端 WS 寿命离散**（同窗口实测）：697.6s / 504.5s / 333.1s / 260.0s / 254.9s / 182.1s / 151.1s / 146.6s / 126.2s / 114.4s / 97.7s / 87.3s / 29.5s / 23.9s / 12.2s / 9.0s / 7.0s。长寿命达 700s（终端 WS 有 30fps `cell_frame` 恒定推送，天然不空闲），短寿命多与切会话/失焦相关。
- **链路两端都没有 WS 心跳**：`src/ws/terminal.rs:18,48` 定义了 `ping` / `pong`，但 `ServerControl` 被标 `#[allow(dead_code)]`（未接线），前端也没有任何发送方；ACP WS 无 ping 处理。即：完全空闲的连接没有任何字节往来。
- **cloudflared 侧无显式超时配置**：`/etc/cloudflared/config.yml` 无 `originRequest` 段（全默认值），版本 2026.5.0，`--no-autoupdate`。
- 已知反证：上一次排查用裸 WS 探针经公网空闲 260s+ 未被断 → 与「CF 固定 100s 空闲超时」的常见说法冲突。**该探针的端点/流量形态与真实链路是否等价未验证**，这是本次必须先补的控制变量。

### 根因候选（互斥假设）

| # | 假设 | 预测 | 现有证据 |
|---|------|------|---------|
| H1 | 隧道链路（CF 边缘或 cloudflared）存在 ~125s 空闲窗口 | 完全空闲必在 ~125s 被杀；周期性发字节可无限延长 | 支持：释放态 11 次命中 125.2s。反证：turn 内有流量的连接也出现 125.3s |
| H2 | 存在与流量无关的连接寿命上限 | 无论有无流量都死在同一时刻 | 被削弱：463s / 698s / 505s 均存在 |
| H3 | 客户端主动重建（blur/idle 拆连、focus 重连、退避抖动） | 断开时刻与页面事件相关，且服务端看到干净关闭而非 reset | 不支持：服务端观察到的是 reset，非关闭握手 |
| H4 | 移动端网络/运营商 NAT 侧回收 | 只在移动端重现，桌面端/直连不重现 | 未验证（用户报告明确提到移动端） |

结论：**前提未确证，先测后定**，不先写心跳。

## 范围与优先级

| 优先级 | 目标 | 要点 |
|--------|------|------|
| P0 | 用受控实验判定 H1–H4 归属 | 四格矩阵：{直连, 公网} × {完全空闲, 每 30s 心跳}，各 ≥15min |
| P1 | 按判定结果决定是否接入心跳 | 若 H1 成立：接线 `ping`/`pong` 并给 ACP WS 补同款；若 H3 成立：改重连/拆除策略而非加心跳 |
| P2 | 移动端专项（若 H4 成立） | 前台/后台切换、网络切换时的重连体验，另立 |

### 不纳入范围

- 改动 CF / cloudflared 运维配置（不在代码库内，且未证实前不动；若 H1 确证且心跳不可行，再另行评估 `originRequest` 参数）。
- 本轮不新增自动重连机制（已有；本计划只解决断因）。

## Phase 0：受控探针（先行，产出判定）

**必须控制的变量**（上次失败的教训）：端点用**真实服务端点**（正式版 9077 的 `/ws/terminal`、`/ws/acp`），不用泛化 echo 服务；同一探针脚本跑四格；每格记录「首字节时间、首次断开时刻、断开形态（close code / reset）」。

| 格 | 目标 | 期望判定 |
|----|------|---------|
| A 直连 + 空闲 | 排除隧道 | A 不死而 B 死 ⇒ 断因在隧道侧（H1） |
| B 公网 + 空闲 | 复现线上 | B 稳定 ~125s ⇒ H1 成立 |
| C 公网 + 每 30s 一个 ping | 验证「有流量即延长」 | C 显著长于 B ⇒ H1 坐实，且心跳是有效对策 |
| D 公网 + 持续 30fps 流量 | 模拟终端 WS | D 与 C 同档 ⇒ 与流量密度无关，回到 H2 |

补充采集：断连期间 `cloudflared` 日志、`ss -tnp` 到 CF 边缘的连接状态、服务端 `ResetWithoutClosingHandshake` 出现时刻与探针观测对齐。

**判定表**：A 死 ⇒ 与隧道无关（查服务端/客户端）；仅 B 死 ⇒ H1；C、D 也死 ⇒ H2；只在移动端死 ⇒ H4。

## Phase 1：心跳（条件性，Phase 0 后定稿）

- **D1 间隔**：取实测窗口的 ≤1/3（若 125s 确证则取 30s），常量集中定义，禁止散落魔法数字。
- **D2 方向**：客户端发起 `ping`、服务端回 `pong`（复用 `ClientControl::Ping` / `ServerControl::Pong`，顺带清理 `dead_code` 标注）；服务端不做主动 ping（避免与既有推送循环耦合）。
- **D3 覆盖范围**：终端 WS 与 ACP WS 都要（同一失败模式已同时在两条链路上观察到），但抽共享 helper，不复制粘贴。
- **D4 半开检测**：连续 N 个周期无 `pong` 才判定断开，避免误杀；与既有自动重连退避的交互需在实现时确认（重连前先清零心跳状态，防重复重连）。
- **翻盘条件**：若 Phase 0 判定为 H2（硬上限）或 H3（客户端主动），则本 Phase 改为相应策略，心跳不落。

## 风险与降级

| 风险 | 缓解 |
|------|------|
| 探针仍在「非真实链路」上跑，结论不可迁移 | 强制用真实端点 + 与线上同一域名；A 格作对照组 |
| 心跳把移动端电耗/流量拉高 | 间隔 ≥30s、页面隐藏时暂停（与既有 blur/idle 拆除策略一致） |
| 心跳掩盖真实断因 | Phase 0 未出结论前不写心跳代码 |
