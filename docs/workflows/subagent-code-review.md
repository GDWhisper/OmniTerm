# Subagent Code Review

> **Agent 触发条件**：用户要求「用子代理 / 子 agent 审查代码」「review 一下」「复查这段改动」，
> 或实现完成后需要一次**独立于实现者**的评审时——**先读本文，再派发子代理**。
> 禁止在没有本文提示词的情况下裸派子代理做审查（裸派 = 只得到通用审查，本文 §3 的项目红线全部漏检）。
>
> **何时维护**：新增审查维度 / 调整提示词模板或输出格式 / 发现新的审查盲区后回写本表与本文。

本文是**给审查者子代理的提示词集 + 父 agent 的派发协议**。模板可整段粘贴（§2），
项目专用检查项以本文为唯一真源，提示词内只引用不复制。

---

## 1. 机制与硬约束

| 角色 | 职责 | 禁止 |
|---|---|---|
| 父 agent（收到审查要求的那个） | 装配提示词、交代范围与验收点、回收结论并逐条处置、向用户如实汇报 severity | 替审查者筛选问题、把 blocker 降级成"后续优化"、跳过审查直接宣称完成 |
| 审查者子代理 | 只读核查代码、给证据、给结论 | 修改任何文件、接受实现者摘要当事实、只读摘要不读源码 |

**硬约束：**

1. **审查者必须是独立子代理实例**（`reviewer` 类型，只读），**不得复用实现者的会话或上下文**。
   让写着代码的那一方回头审自己，只会得到确认偏差，不是审查。
2. **审查范围由父 agent 显式给出**（§2.1 四项必填）。父 agent 必须交代范围，不得用"看看我的改动"代替，
   否则审查者会漏掉未出现在摘要里的文件（新增文件、迁移、文档、locale、配置）。
3. **修复由实现方做，复查用 §2.4 的 T3 块**（resume 同一审查者，保留其上下文与已发现的坑），
   不得让实现者自述"已修复"结案。
4. **审查者给出的每条问题都必须带 `file:line` + 实际代码引用**。无法定位到行的判断标注「推测」并降级为 nit。
   不确定必须说「不确定」，禁止用模糊表述凑结论。

## 2. 提示词模板

### 2.1 父 agent 派发前必须备齐的四项

| 项 | 内容 | 反例 |
|---|---|---|
| 变更范围 | diff 基线（commit/tag/branch）+ 文件清单；含未提交改动时给文件清单 | "我改了一些东西" |
| 原始需求与验收点 | 用户要什么、怎样算做到 | 只给代码不给需求 |
| 关联方案文档 | 命中的 `docs/dev/plans/*.md`、架构文档、ADR 路径 | 让审查者自己猜设计意图 |
| 已执行的验证 | 跑过的命令 + 实际结果（通过/失败/未跑） | 声称"测试通过"而没跑 |

### 2.2 T1 — 变更审查（默认模板，整段粘贴）

```text
你是本次改动的独立审查者（只读，禁止修改任何文件；git 只允许只读子命令）。

【变更范围】{diff 基线 或 文件清单}
【原始需求与验收点】{用户要求 + 怎样算完成}
【关联设计文档】{docs/dev/plans/... 、架构文档路径，无则写"无"}
【实现方已执行的验证】{命令 + 实际结果；未跑写"未跑"}

【第一步 · 先读规则】按改动涉及面取用，命中即读，读完全部再开始审：
- AGENTS.md（工程准则、核心规则、配置统一管理、测试约定、文档索引）
- docs/dev/performance-and-safety.md（性能红线 P1-P6 / 安全红线 S1-S5，及文末案例索引）
- docs/architecture/backend.md 或 docs/architecture/frontend.md（按改动所在侧）
- docs/workflows/integration-checklist.md（改动涉及 spawn 抽象或新增枚举变体时）
- docs/architecture/frontend-patterns.md、docs/visual-design/ui-style-guide.md（改动涉及 UI 时）
- docs/workflows/agent-edit-manual.md（改动命中已收录组件时，核对是否漏改文件）
- 本次改动命中的 docs/dev/plans/*.md（核对是否违背已定案决策）

【第二步 · 逐项核对】读 docs/workflows/subagent-code-review.md §3 清单，按维度逐项过，
不得跳项；不适用的维度写"不适用 + 原因"，不得静默略过。

【第三步 · 读源码，不读摘要】逐个文件读改动及其调用方/被调用方。实现方给你的摘要不是证据，
必须以文件内容为准。必要时用 codegraph 查 callers / impact 确认影响面。

【第四步 · 输出】按 §4 格式输出。每条问题必须含：severity、file:line、实际代码引用、
违反的项目规则（AGENTS.md 条目或 P/S 红线编号）、建议修法。禁止"建议优化一下"这类无锚点结论。

要求：对抗性立场——先假设改动有问题，去证伪实现方的"已完成/已修复"主张。
不确定的结论必须显式标注"不确定"及不确定的原因。
```

### 2.3 T2 — 专项深审（附在 T1 之后，按改动性质取用）

```text
【加挂 A · 性能与容量】改动涉及累积结构 / 持久化写入 / 跨层传输 / 流式链路时：
对每个累积结构回答三问（上限是什么、超限怎么办、哪个测试守住它），
核对上限维度是否匹配真实增长维度（条目数上限是否被单条体积击穿），
核对截断是否标注省略量、是否按字符边界切，核对无界数据源的全部出口量级。
P6：容量/吞吐类改动的验证是否只在短任务、小数据下做过？是则按未验证上报。

【加挂 B · 安全】改动涉及外部输入（用户输入、文件内容、agent 通知、子进程输出）时：
路径/命令/HTML/SQL 是否 sanitize 或走白名单；有无吞异常掩盖根因；
凭据、token、密钥是否可能进日志或明文入库；
新增 API 端点 / WebSocket 是否接在鉴权链路上（不能只有中间件定义）；
是否存在越界访问（以会话 workspace 为根）。

【加挂 C · 协议与多实现兼容】改动涉及 agent 协议、事件/帧、可选字段、枚举变体时：
可选/可能缺省的字段与能力是否显式回退兜底；是否把单一实现的行为当成了约定的全部；
新增枚举变体的跨层不变量是否有真进程级验证（不依赖协议层 mock）；
实现差异是否已沉淀到对应索引文档而非只写在代码注释里。

【加挂 D · 前端】改动涉及 UI / 状态时：
样式是否只用设计 token（有无硬编码色值、font-family、内联阴影）；
是否复用既有 pattern（弹出面板、抽屉、动作注册表、上下文菜单）而非新造；
i18n 是否两个 locale 同步；状态是否落在正确的 store 而非组件局部复制。

【加挂 E · 测试与验证】核对新增逻辑/边界/上限是否有对应测试；
核对实现方是否改动或删除了既有断言来让测试通过（这是 blocker 级）；
核对验证命令是否按本仓约定执行（前端类型检查用 tsc -b、非裸 tsc；性能基准不进 pnpm test）。
```

### 2.4 T3 — 修复后复查（resume 同一审查者）

```text
上一轮问题清单中标记为 {blocker/major 的条目} 已修复，修复范围：{commit 或文件清单}。
请只做两件事：(1) 逐条核对每个问题是否真被修复（读代码，不信描述）；
(2) 检查修复本身是否引入新问题或回归。
同时确认上一轮列出的「未验证项」是否有新的验证结果。
输出：逐条给出 已修复 / 未修复 / 部分修复（含证据），并给出更新后的结论。
```

## 3. 项目专用审查清单

> 引用而非重述既有规则：核对时以原文为准，本文只规定"审什么、要什么证据"。

### 3.1 需求与完成度

| 检查项 | 证据要求 |
|---|---|
| 验收点逐条达成？ | 每个验收点指出实现位置与代码证据 |
| 有无 TODO / 占位 / stub / mock 冒充完成？ | grep 改动范围，列出命中行 |
| 有无范围外改动（顺手重构、顺带改风格）？ | 对照文件清单标出非需求改动，按「最小改动」判 severity |
| 有无把问题换成更简单的问题交差？ | 对照原始需求描述判断是否偷换目标 |

### 3.2 架构与分层

| 检查项 | 依据 |
|---|---|
| 后端是否越层调用（路由层直接操作引擎/PTY 细节、绕过 session 引擎抽象）？ | `docs/architecture/backend.md` |
| 文件路径操作是否统一走既有路径安全函数？ | 同上 + `docs/dev/performance-and-safety.md` S1 |
| 前端共享函数 vs 自定义 Hook 的提取判据是否用对？ | `docs/architecture/frontend.md` |
| 是否该复用已有前端 pattern 却新造一套？ | `docs/architecture/frontend-patterns.md` |
| 是否把一件事拆成三件却没缩小影响面（过度设计）？ | AGENTS.md 工程准则 7 |

### 3.3 技术债红线（发现即 blocker/major，不得降级为 nit）

| 红线 | 证据要求 |
|---|---|
| Copy-Paste（同一判断/转换/校验出现 ≥2 处） | 列出所有出现点 |
| 魔法数字 / 硬编码（端口、域名、阈值、尺寸、路径） | 引用硬编码行 + 应落位置（常量/配置/`.env.local`） |
| 死代码（未被调用的新增函数、永假分支） | 用 callers 查询证实 |
| 无界累积（缺上限 / 上限维度错 / 静默丢弃 / 截断切断 UTF-8） | 按 P1 三问逐条回答 |
| 吞异常掩盖根因（空 catch、无日志的 `ok()`、错误转默认值继续跑） | 引用行 + 掩盖后的后果 |

### 3.4 安全与外部输入

按 S1-S5 逐条核对；重点：新端点/WS 的鉴权**是否真挂在链路上**（仅有中间件定义不算通过），
凭据是否可能进日志/明文入库，外部输入是否在进入路径解析、命令构造、HTML 渲染、SQL 前完成校验。
参照 `docs/reference/auth-not-enforced.md` 的历史教训。

### 3.5 多实现兼容性

按 AGENTS.md 工程准则 8：可选/可能缺省的字段、通知、能力是否显式回退；
是否把单一实现行为当成了约定的全部事实；实现差异是否沉淀进索引文档。
涉及 spawn 抽象或枚举新变体时，强制过 `docs/workflows/integration-checklist.md` 清单 A/B，
并核对验证是否落在**真进程 / 真 OS 状态**上（协议层 mock 全过不算通过）。

### 3.6 前端专项

- 设计 token：无硬编码色值 / `font-family` / 组件内联阴影；用既有像素组件与工具类。
- 交互契约：新弹层是否遵守既有定位常量与滚动容器约定。
- i18n：两个 locale 文件同步新增，key 命名一致。
- Hooks 约定：handler 定义顺序、依赖数组完整、默认不 memoize、订阅/定时器/在途请求 cleanup。
- 性能基准不进常规测试通道。

### 3.7 测试与验证

| 检查项 | 证据要求 |
|---|---|
| 新增逻辑/边界/上限有测试？ | 给出测试名与断言内容 |
| 是否有测试被削弱/删除以通过？ | diff 中测试断言的变更逐条说明（blocker 级） |
| 验证命令是否真跑过、是否按本仓约定？ | 前端类型检查用 tsc 项目构建、lint、格式化与静态检查、Rust 全量测试（依赖 tmux） |
| 容量类改动是否做过真实负载验证？ | 长任务/大数据量证据，缺失按未验证上报 |

### 3.8 流程与配置同步

| 检查项 | 依据 |
|---|---|
| 改动是否命中某文档索引的「何时维护」触发点（新 API / 新组件 / UI 规范 / spawn 变体 / 性能安全红线）？命中即应同步 | AGENTS.md 文档索引表 |
| 数据库迁移是否只新增、未修改历史文件？ | AGENTS.md 关键目录 |
| 版本号是否走统一脚本（未手改前端包描述文件）？ | AGENTS.md 配置统一管理 |
| 分支专属变量 / 密钥是否未入仓？后端配置是否只走命令行参数或专用前缀环境变量？ | 同上 |
| 提交信息前缀是否符合约定（功能/修复/文档/杂项）？ | AGENTS.md 核心规则 1 |
| 变更日志是否只记实质性功能改动（文档改动不记）？ | AGENTS.md 核心规则 2 |

## 4. 输出格式

与内置审查者格式兼容（四段式为主线，后两段为本文扩展），段落顺序不得调整：

```text
### Summary
一段话：结论（approve / approve with comments / request changes）+ 前 1-3 条理由。

### Issues
每条格式：
- [severity] file:line — 问题描述
  - 证据：<实际代码引用 / 命令输出>
  - 违反：<AGENTS.md 条目 或 P/S 红线编号；无对应规则则写"无（通用工程判断）">
  - 建议修法：<具体到改动点>

severity 定义：blocker = 合并前必须修（正确性、安全、数据丢失）；
major = 合并前应修（显著正确性风险、性能、可维护性）；
minor = 值得修但不阻塞；nit = 个人偏好。

### Suggestions
非阻塞改进（重构机会、命名、结构清理），不带 severity。

### Critical Files
3-5 个最值得二次确认的文件（绝对路径）+ 一行理由。

### 未验证项
本次审查未能覆盖或未能验证的部分：未跑的命令、未读的实现分支、依赖真实负载才能暴露的行为、
需要用户判断的取舍。写"无"也必须有（表示确实评估过）。

### 文档同步
按 §3.8 命中情况给出：需更新而没更新的文档（含具体文件），或"无需同步 + 理由"。
```

## 5. 审查者反模式（出现即视为审查无效，需重派）

| 反模式 | 后果 |
|---|---|
| 只看实现者摘要 / 只扫 diff，不读文件与调用方 | 漏掉上下文导致的正确性问题 |
| 接受"已完成 / 已修复"的表述，不读代码验证 | 放过假完成 |
| 把项目红线问题降级为 nit（"后续可以优化"） | 技术债合法化 |
| 只报风格与命名，不碰正确性、容量、安全 | 高代价问题漏检 |
| 无 `file:line` 的结论 / 无证据的"看起来没问题" | 无法复核 |
| 修改文件或运行有副作用的命令（安装、迁移、清理） | 越权且有风险 |
| 不确定却说"没问题" | 假阴性 |

## 6. 父 agent 回收结论

1. 逐条回应每个 blocker / major：已修（附新 commit）/ 不修（附理由）——禁止静默忽略。
2. 「未验证项」必须转成显式待办或向用户披露的风险，不得留在报告里自动消失。
3. 向用户汇报时保留 severity 与影响面，不做"基本没问题"式软化。
4. 审查者为独立子代理这一事实要向用户说明（避免被误读为自评）。
